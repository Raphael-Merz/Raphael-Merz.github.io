Editing your website

A walkthrough of how this repository (Raphael-Merz.github.io) is put together, which file controls which part of the site, and how to make the usual changes. This file sits in the repo root, which Hugo doesn't publish, so it won't show up on the live site.

1. How the site works

The site is built with Hugo, a static site generator, using the HugoBlox "Academic CV" template. You never write HTML. You edit:

  • YAML files for settings and structured data (your name, colors, menu items, education list, …)
  • Markdown files for pages (blog posts, project pages, the homepage layout)

The template's actual code (page layouts, CSS, the "blocks" the pages are built from) is not in your repo. It's a Hugo module that gets downloaded at build time (see go.mod and config/_default/module.yaml). So you configure the template but don't edit its code. That's why there's no big themes/ or layouts/ folder.

Publishing works like this:

Edit files→ Commit & push to main→ GitHub Action builds the site with Hugo→ Live at raphael-merz.github.io (a few minutes)

The workflow that does this is .github/workflows/deploy.yml. You can watch it under the Actions tab of the repo on GitHub.

3. Markdown, YAML & front matter (the 2-minute version)

Every page in content/ is a Markdown file that starts with a front matter block between --- lines. The front matter is YAML and holds the page's settings. Everything below it is the page text in Markdown.

---
title: My first post          # front matter (YAML): settings
date: 2026-11-17
tags: [Effect sizes]
---

Here is the **body** of the page, written in Markdown.   ← content

Page bundles

Most pages are a folder containing an index.md plus any images or files that belong to it. The folder name becomes the URL:

content/blog/my-first-post/
├── index.md        → raphael-merz.github.io/blog/my-first-post/
├── featured.jpg    → thumbnail on the blog list + header image
└── figure1.png     → use in the text as ![caption](figure1.png)

A file named _index.md (with underscore) is the list page for a section, e.g. content/blog/_index.md is the page at /blog/ that shows all posts.

Landing pages and blocks

Pages with type: landing (the homepage, the Blog page, the Projects page) don't have body text. They have a list of sections:, and each section is a block such as a biography, a markdown text box, or a grid of posts. You rearrange a page by reordering, adding, or commenting out blocks. The full block catalogue is at hugoblox.com/blocks.

YAML gotchas

  • Indentation matters and must be spaces, never tabs. Most broken builds come from a misaligned line.
  • Put text containing : or # in quotes: title: 'Effect sizes: a primer'.
  • For multi-line text use | and indent the following lines (as in your bio:).
  • # starts a comment. That's how blocks and menu items are currently switched off.

4. Where to edit what

About text, name, role, links, interests, education

data/authors/me.yaml

The "About me" box on the homepage is built from this file, not from content/_index.md. The relevant fields:

name:
  display: Raphael Merz          # big name on the homepage
role: PhD Candidate              # line under the name
status:
  icon: "📈"                     # little emoji badge on the photo
bio: |                           # ← the "About me" text; Markdown links work
  Hi, I'm Raphael, a PhD researcher ...

  Second paragraph after a blank line.
affiliations:
  - name: Eindhoven University of Technology
    url: https://research.tue.nl/...
links:                           # the icon row under your name
  - icon: brands/github
    url: https://github.com/Raphael-Merz
interests:                       # "Interests" list
  - Meta-Science
education:                       # "Education" list; newest first
  - degree: PhD Meta-Science (in progress)
    institution: Eindhoven University of Technology
    start: 2025-10-01
    summary: |
      Optional text, Markdown allowed.
    button:                      # optional button under the entry
      text: Download thesis
      url: https://...
      icon: hero/arrow-down-tray

Link icons come from a few icon sets, written as set/name:

  • brands/…: logos like brands/github, brands/linkedin
  • academicons/…: academic logos like academicons/orcid, academicons/google-scholar
  • no prefix or hero/…: general icons like at-symbol, hero/arrow-down-tray
  • custom/…: your own SVGs from assets/media/icons/custom/. custom/bluesky uses bluesky.svg. To add one, drop an SVG in that folder and reference it by filename without .svg.

The section headings on the homepage ("About me", "Education", "Interests") are set in content/_index.md under headings:.

Profile photo

assets/media/authors/me.png

Replace this file with a new image of the same name. The filename matches the author slug me. Use a roughly square image. Hugo resizes it, so the full-resolution file is fine. Size and shape (circle/square/rounded) are set in content/_index.md under design: avatar:.

Homepage layout

content/_index.md

Right now the homepage has one active block, resume-biography-3 (photo + name + bio + interests + education). Things you can change there:

  • headings: renames the "About me" / "Education" / "Interests" titles.
  • design: background: gradient_mesh: enable: turns the colored gradient background on or off.
  • design: name: size: and design: avatar: size/shape: control the name and photo size.
  • button: (commented out) adds a "Download CV" button under the bio.

Below it are commented-out blocks you kept from the template: a "📚 My Research" markdown block, "Featured Publications", "Recent Publications", and "Recent & Upcoming Talks". To enable one, remove the # from each of its lines while keeping the indentation consistent with the active block above (each block starts with - block:, two spaces then a dash).

Watch out: in the "Recent Publications" block (around lines 57–66), the content:/design: lines are commented with a different indentation ( # content:) than the # - block: collection line above them. When you uncomment it, check that content: and design: line up with those of the bio block, or the build fails.

The last block, cta-card ("Build your own academic website like this"), has demo: true. It only shows on HugoBlox's own demo site, not on yours, so you can leave it or delete it.

If you give a block an id: (e.g. id: papers), you can link to it from the menu with url: /#papers.

Add an item by copying a three-line entry, remove one by commenting it out. External links work too (url: https://osf.io/...). Header behavior (sticky, alignment, search, dark-mode toggle) is in params.yaml → header: (see §5).

Removing a menu item only hides the link. The page itself still gets built and stays reachable by URL and by the site search. See §6 for how to actually unpublish something.

Blog: list page and new posts

content/blog/_index.md

The /blog/ page. Change the title, the intro text (text:, already personalised), and the grid design (columns, show_date, show_read_time, …).

content/blog/<post-name>/index.md

To write a new post:

  1. Create a folder in content/blog/ with a short, URL-friendly name, e.g. content/blog/equivalence-tests/.
  2. Inside it, create index.md with front matter like this: 
    ---
title: What equivalence tests can and can't tell you
summary: One or two sentences shown on the blog overview card.
date: 2026-11-17
authors:
  - me
tags:
  - Effect sizes
  - Statistics
draft: true          # remove or set false when ready to publish
image:
  caption: ''        # caption for featured.jpg, optional
---

Your text in Markdown. Use ## for section headings.

![Figure caption](figure1.png)
  3. Optionally add featured.jpg (or .png) to the folder. It becomes the card image and the post header.
  4. Commit and push. Posts appear newest-first by date.

The template posts also use an optional cover: block for a full-width banner image from a URL. Copy it from content/blog/get-started/index.md if you want that look. Easiest start: copy one of the existing template post folders, rename it, and replace the text.

The template posts double as a formatting reference: callout boxes (> [!NOTE]), Mermaid diagrams, mind maps and to-do lists (project-management), charts and embeds (data-visualization), audio (teach-courses), and Jupyter notebooks (notebook-onboarding). Look at how they do it before deleting them.

Publications

Not shown in the menu or on the homepage right now, but the template supports two ways to add papers:

  1. By hand: one folder per paper in content/publications/. Copy journal-article/ (or preprint/, conference-paper/) and edit the front matter: title, authors (use me for yourself), date, publication_types, publication: name, abstract, links (pdf, code, dataset, …). Add a cite.bib to power the "Cite" button.
  2. From BibTeX (automatic): put a file called publications.bib in the repo root and push. The import-publications.yml workflow converts it into publication folders and opens a pull request that you review and merge. For this to work, GitHub must allow Actions to create PRs: repo Settings → Actions → General → Workflow permissions → tick "Allow GitHub Actions to create and approve pull requests".

To show them on the site, uncomment the publications blocks in content/_index.md and/or add a menu item (url: /publications/ or /#papers). Set featured: true in a paper's front matter to include it in "Featured Publications".

CV PDF and other downloadable files

static/uploads/resume.pdf

The "CV" menu item links straight to this file. Replace it with your own CV under the same name, or rename it and update the URL in menus.yaml. Anything else you put in static/ is published at the same path. static/uploads/slides.pdf → /uploads/slides.pdf.

Talks, courses, slides, experience page

  • Talks: content/events/, one folder per talk (see example/index.md for the fields: event_name, location, event_start, links, …).
  • Slides: content/slides/. Markdown slide decks shown with reveal.js. example/index.md documents the options.
  • Courses: content/courses/. The hugo-blox/ folder is a documentation-style example course.
  • Experience: content/experience.md is a page at /experience/ that displays the experience, skills, awards and languages lists from data/authors/me.yaml. Those lists still contain TODO placeholders. Fill them in (or remove them) before linking the page; the menu entry for it is already there, commented out.

5. Global look & settings

config/_default/params.yaml

Everything site-wide lives under the hugoblox: key in this file. The file is well commented. These are the parts you're most likely to touch:

Identity

identity:
  name: "Raphael Merz"          # navbar, footer, browser tab title
  tagline: "PhD Candidate at Eindhoven University of Technology"
  description: "..."            # shown by search engines / link previews
  social:
    bluesky: "raphaelmerz.bsky.social"

Colors and theme

theme:
  mode: light          # light | dark | system (follow visitor's OS)
  pack: minimal        # the base color theme
  colors:
    primary: "#D9F2D0" # accent color: hex code or a Tailwind name like "emerald"
    secondary: ""
    neutral: ""        # tint of the grays
  colors_light: {}     # optional overrides for light mode only
  colors_dark: {}      # optional overrides for dark mode only
  surfaces:            # optional: background / header / footer colors
    background: ""
    header: { background: "", foreground: "" }
  • Theme packs available in the template: default, minimal, contrast, coffee, cupcake, dracula, marine, matcha, retro, solar, synthwave. You can also mix packs: pack: { light: "minimal", dark: "dracula" }.
  • Primary color is used for links, buttons and accents. Tailwind color names (green, emerald, teal, indigo, …) give you a whole range of shades automatically. Your current #D9F2D0 is a very pale green, so links and buttons in that color may be hard to read on a white background. If that bothers you, try a darker hex or a name like "green".
  • mode: light sets the default, but header: theme_toggle: true still lets visitors switch to dark mode. Set it to false to lock the mode.

Fonts and shapes

typography:
  pack: "academic"     # academic | developer | editorial | geometric | humanist | modern | system
layout:
  radius: "md"         # corner rounding: none | sm | md | lg | full
  spacing: "spacious"  # compact | comfortable | spacious
  avatar_shape: circle # circle | square | rounded

Header, footer, copyright

header:style (navbar / navbar-simple / minimal), sticky, align, search, theme_toggle, theme_picker, language_switcher, and an optional call-to-action button (cta).
footer:style (minimal / columns / centered), custom text (HTML allowed), language_switcher.
copyright:The notice text ({year}, {name}, {license} placeholders) and which Creative Commons license applies to your content.

6. Template leftovers to be aware of

Hiding something from the menu doesn't remove it. Every page under content/ is built and published, and it's reachable by URL, by the site search, and by search engines. As of now, these template pages are live on your site:

  • Blog: 6 template posts (data-visualization, get-started, notebook-onboarding, project-management, second-brain, teach-courses). They are visible because Blog is in the menu.
  • Projects: pandas, pytorch, scikit, plus the template title/intro on the Projects page. Also visible via the menu.
  • Not in the menu but still published: 3 example publications, the example talk (/events/example/), the example course (/courses/hugo-blox/), the example slide deck (/slides/example/), and /experience/ with the TODO entries from me.yaml.
  • Other: static/uploads/resume.pdf (check it's your CV), config/_default/params - Kopie.yaml (unused copy), README.md (template text).

Three ways to take something offline:

  1. Delete the folder/file. Simplest, and it's still in your git history if you want it back.
  2. Add draft: true to a page's front matter. Drafts are not published.
  3. Switch off a whole section by adding this to its _index.md front matter. It's the same trick content/authors/_index.md already uses: 
    build:
  render: never
cascade:
  build:
    render: never
    list: never

7. Publishing & previewing

Publishing

  1. Edit files (in VS Code, or directly on github.com with the pencil icon).
  2. Commit and push to the main branch.
  3. On GitHub, open the Actions tab. "Deploy website to GitHub Pages" runs. A green check means it's live, usually within a few minutes. Refresh the site with Ctrl+F5 if you still see the old version.

Previewing before you publish (optional)

You can check changes locally before pushing. Hugo isn't installed on this computer yet, so this needs a one-time setup:

  1. Install Hugo extended (version 0.161 or newer, matching hugoblox.yaml), Go (Hugo modules need it), and pnpm. Node.js is already installed.
  2. In the repo folder, run pnpm install once.
  3. Run hugo server and open http://localhost:1313. The page reloads every time you save a file. Drafts can be previewed with hugo server -D.

Alternatives without installing anything: open the repo in a GitHub Codespace (the .devcontainer/ folder sets everything up), or use the Ownable VS Code extension the template recommends for visual editing.

Template updates

Every Monday the upgrade.yml workflow checks for a newer HugoBlox version and, if there is one, opens a pull request titled "⬆️ Upgrade HugoBlox Modules". Merging it updates the template. Your content isn't touched, but it's worth glancing at the site afterwards. This also needs the "Allow GitHub Actions to create … pull requests" setting from §4.

8. When something breaks

  • Red ✗ in the Actions tab: the build failed and your previous version stays online. Click the failed run → "build" → "Build with Hugo" and read the error. It usually names the file and line.
  • Most common cause: YAML indentation, a tab character, or an unquoted : in a title. Compare with a working file.
  • Change not showing: check you edited the right file. Remember params - Kopie.yaml does nothing, and the bio lives in me.yaml, not _index.md. Also check that the page doesn't have draft: true and that its date isn't in the future (future-dated pages aren't published).
  • Undo: every push is a commit, so you can always revert to an earlier version from the git history.
